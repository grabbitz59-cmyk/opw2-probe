# Сырой PPG на OPW2: что удалось выяснить

Короткий ответ: **сырой PPG (`PPG_RAW_IR0/R0/G0`) в том виде, как его отдаёт
`SensorManager`, не содержит кардио-компоненты.** HRV/RR из него не достать.
«Умный» триггер надо строить на passive HR из Health Services + актиграфии.

## Условия решающего эксперимента

- Захват: 60 с, 2991 событие, `fs=50.0 Гц`, три сенсора, файл 741 КБ
  (`tools/ppg_hr.py` + `PpgCaptureService`).
- Контакт подтверждён системой: `HrAccuracy(sensorStatus=ACCURACY_HIGH)`, passive HR
  непосредственно перед захватом **82 bpm**, сразу после — 89/93 bpm.
  То есть истинный пульс в момент записи ≈ 82–93 уд/мин (1.37–1.55 Гц).

## Что показали данные

| Проверка | Результат |
|---|---|
| Доминирующий пик спектра во всех каналах | **≈52 «уд/мин»** (0.87 Гц), SNR 3–7 |
| Пик в диапазоне истинного пульса 1.37–1.55 Гц | **отсутствует** (лучшее — 85 «уд/мин» с SNR 3.0 на `v9`) |
| Корреляция `v2/v3/v4` | **0.89–0.98** — это один сигнал, а не разные каналы |
| Корреляция `v6..v9` между собой | 0.40–0.75 — вторая группа значений |
| `v6..v9` vs `v1..v4` | около нуля — разные величины, не «сырое/фильтрованное» одного сигнала |
| Форма сигнала после детренда | медленный дрейф/ступеньки, без повторяющейся пульсовой волны |
| Захват без контакта (`NO_CONTACT`) | плоская линия со ступенькой |

Наблюдаемые 52 «уд/мин» не совпадают ни с истинным пульсом, ни с дыханием
(это 0.87 Гц — слишком быстро для дыхания) — это артефакт декодирования
16 значений события, а не физиология.

## Почему так

16 значений на событие выглядят как упакованная структура (маркеры `v0=v5=4`,
группы `v1..v4`, `v6..v9`), а не как 16 последовательных сэмплов. Ни одна из
проверенных раскладок не дала кардио-компоненты:

- `v1..v4` как 4 последовательных сэмпла → 200 Гц;
- каждый столбец как отдельный канал → 50 Гц;
- `v6..v9` как AC-составляющая → 50/200 Гц;
- склейка всех восьми → 400 Гц.

Вероятно, вендорский слой (`com.google.wear.sensor.ppg*`) требует своей сессии
измерения, а `PPG_RAW_*` отдаёт служебные/промежуточные значения. Проверять это
дальше имеет смысл только если найдётся вендорский путь старта измерения;
для будильника это не критично.

## Что из этого следует для продукта

Работает и доступно:

- **passive HR** из Health Services: ~3551 записи/час, `ACCURACY_HIGH/LOW/MEDIUM`,
  свежий HR в 91 % окон ночного лога;
- **акселерометр**: движение/актиграфия (медиана `std` 0.35 на спокойной руке,
  `moves/n` 0.27–0.8 %);
- **точный будильник** через `setAlarmClock` (переживает переустановку APK).

Не работает: HRV/RR из сырого PPG; `android.sensor.heart_rate` (отдаёт 0);
`ppg_hrm`/`ppg_spo`/`ecg` (закрыты); `USER_ACTIVITY_ASLEEP` (система не отдаёт
сон наружу — за 18.7 ч наблюдения пришёл только `PASSIVE`).

Поэтому «умность» строим так: тренд HR (подъём ≥ 8 bpm над медианой 30–45 мин)
+ актиграфия (эпизоды движения) + дедлайн. Это классическая схема, и она
опирается только на те данные, которые реально доступны.
